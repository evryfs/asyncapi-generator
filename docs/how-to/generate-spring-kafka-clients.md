# Generate Spring Kafka clients

This guide generates Spring Kafka producer and consumer interfaces for the
channels of an AsyncAPI contract, together with the payload models they use.
The generated code is a contract: your application implements the interfaces
and owns all Kafka runtime configuration.

## Configure the execution

Client generation needs four settings on a `java` or `kotlin` execution:
`modelPackage`, `clientPackage`, `clientType` `spring-kafka`, and
`clientContract` `interface`.

Maven:

```xml
<configuration>
    <generatorName>kotlin</generatorName>
    <inputSpec>${project.basedir}/src/main/resources/asyncapi.yaml</inputSpec>
    <modelPackage>com.example.accounts.model</modelPackage>
    <clientPackage>com.example.accounts.client</clientPackage>
    <clientConfig>
        <clientType>spring-kafka</clientType>
        <clientContract>interface</clientContract>
    </clientConfig>
</configuration>
```

Gradle (`clientConfig` is shared by all executions and is declared once):

```kotlin
asyncApiGenerator {
    clientConfig {
        clientType.set("spring-kafka")
        clientContract.set("interface")
    }
    executions {
        register("accounts") {
            generatorName.set("kotlin")
            inputSpec.set(file("src/main/resources/asyncapi.yaml"))
            modelPackage.set("com.example.accounts.model")
            clientPackage.set("com.example.accounts.client")
        }
    }
}
```

CLI:

```sh
asyncapi-generator \
  --input-spec src/main/resources/asyncapi.yaml \
  --generator-name kotlin \
  --model-package com.example.accounts.model \
  --client-package com.example.accounts.client \
  --client-type spring-kafka \
  --client-contract interface
```

Use `generatorName` `java` for Java interfaces and models.

## What is generated

For each channel, the generator writes a producer interface to
`<clientPackage>.producer` and a consumer interface to
`<clientPackage>.consumer`, named after the channel, for example
`AccountUpdatedProducer` and `AccountUpdatedConsumer`. Each message of the
channel gets one method in each interface:

- Producer `send<Message>(payload, key, headers...)` returns
  `CompletableFuture<RecordMetadata>`. The generated default returns a future
  that fails with `UnsupportedOperationException` until you override it.
- Consumer `listen<Message>(payload, receivedTopic, receivedKey, headers...)`
  has a no-op default. Override it and add `@KafkaListener` to the
  implementation method.
- Message headers become `@Header` parameters; required headers are non-null,
  optional headers are nullable. A Kafka key schema becomes the key parameter
  type.
- Each interface has a topic constant, such as
  `ACCOUNT_UPDATED_TOPIC_ADDRESS`, holding the channel address.

The interfaces do not create beans, register listeners, or configure brokers,
serializers, consumer groups, retries, or transactions. The generated KDoc and
Javadoc include an example implementation. The complete approved output for a
sample contract is linked from
[Spring Kafka contracts with typed headers](../reference/generated-output-examples.md#spring-kafka-contracts-with-typed-headers).

The application needs Spring Kafka on the compile classpath, plus the
dependencies of the generated models (see
[Generate Kotlin and Java models](generate-kotlin-models.md)).

## Generate only producers or only consumers

Producer and consumer interfaces are both generated by default. AsyncAPI
operation actions (`send`, `receive`) do not select them; disable one category
explicitly:

| Frontend | Producers only                                              |
|----------|-------------------------------------------------------------|
| Maven    | `<consumer><enabled>false</enabled></consumer>` in `clientConfig` |
| Gradle   | `consumer { enabled.set(false) }` in `clientConfig`         |
| CLI      | `--no-generate-consumer`                                    |

Disable producers the same way with `producer` or `--no-generate-producer`.
Disabling both fails.

## Add methods for serialized payloads

`additionalPayloadTypes` adds producer methods that accept a payload your
application has already serialized, next to the typed method. The values are
`byte-array` and `string`:

| Frontend | Setting                                                                                                                        |
|----------|--------------------------------------------------------------------------------------------------------------------------------|
| Maven    | `<producer><additionalPayloadTypes><additionalPayloadType>byte-array</additionalPayloadType></additionalPayloadTypes></producer>` |
| Gradle   | `producer { additionalPayloadTypes.set(listOf("byte-array", "string")) }`                                                      |
| CLI      | `--producer-additional-payload-type byte-array` (repeatable)                                                                   |

## Map channel parameters to Spring properties

A channel address such as `accounts.{environment}.updated.v1` contains a
parameter. Map the parameter to a Spring property so the topic constant
becomes `accounts.${kafka.environment}.updated.v1`, which Spring resolves from
your application configuration:

| Frontend | Setting                                                                                                   |
|----------|-----------------------------------------------------------------------------------------------------------|
| Maven    | `<topicParameterProperties><environment>kafka.environment</environment></topicParameterProperties>` in `clientConfig` |
| Gradle   | `topicParameterProperties.put("environment", "kafka.environment")` in `clientConfig`                      |
| CLI      | `--topic-parameter-property environment=kafka.environment` (repeatable)                                   |

Write the property name without `${...}`.

## Add validation annotations

To validate payloads at the interface boundary, configure fully qualified
annotations. `clientContract` annotates each interface and `payloadParameter`
annotates the typed payload parameter of producer and consumer methods; it is
not applied to the additional byte-array and string producer methods:

```xml
<clientConfig>
    <clientType>spring-kafka</clientType>
    <clientContract>interface</clientContract>
    <validationAnnotations>
        <clientContract>org.springframework.validation.annotation.Validated</clientContract>
        <payloadParameter>jakarta.validation.Valid</payloadParameter>
    </validationAnnotations>
</clientConfig>
```

In Gradle use `validationAnnotations { clientContract.set("...");
payloadParameter.set("...") }` inside `clientConfig`; in the CLI use
`--client-contract-validation-annotation` and
`--payload-parameter-validation-annotation`. The application must enable
method validation for these annotations to take effect.

## Share client settings across executions

Client settings in Gradle's `clientConfig`, or in Maven's plugin-level
configuration, reach every execution. Executions without `clientPackage`
ignore them and print the `unused-client-config` warning; silence it with
`suppressedWarnings` as described in
[Configuration warnings](../reference/generator-configuration.md#configuration-warnings).

All client settings and their validation rules are listed in the
[generator configuration reference](../reference/generator-configuration.md#spring-kafka-client-configuration).
